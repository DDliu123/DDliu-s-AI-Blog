## **需求背景**

传统 PRD 的基本板块。

### **问题描述**

用户在进行深度研究时面临以下痛点:

1. 1. **信息****碎片化****严重**: 需要同时查阅多个搜索引擎、网站、文档才能获得全面信息
    
2. 2. **研究效率低下**: 手动收集、整理、分析信息耗时耗力，一个深度研究课题可能需要数小时甚至数天
    
3. 3. **信息质量参差**: 难以快速识别和筛选高质量、可信度高的信息源
    
4. 4. **缺乏系统性**: 缺少结构化的研究方法论指导，容易遗漏重要维度
    
5. 5. **多任务切换困难**: 需要在搜索、阅读、代码执行、记录等多个工具间频繁切换
    

### **目标用户**

- **研究人员**: 需要快速完成文献综述、市场调研、技术分析
    
- **投资分析师**: 需要深度了解行业动态、技术趋势、公司情况
    
- **产品经理**: 需要进行竞品分析、用户研究、市场趋势分析
    
- **内容创作者**: 需要为文章、视频收集素材和数据支撑
    
- **学生群体**: 需要完成课题研究、论文撰写的资料收集
    

### **业务目标**

**核心目标**: 将原本需要数小时的深度研究工作压缩到 15-30 分钟内完成，且质量不降反升。

**量化指标**:

- 研究效率提升: 用户完成一次深度研究的时间从平均 4 小时缩短到 30 分钟以内
    
- 信息覆盖度: 单次研究涉及的信息源数量从平均 5-8 个提升到 20+ 个
    
- 用户满意度: 生成报告的有用性评分达到 4.0/5.0 以上
    
- 用户留存: 7日留存率达到 40% 以上

## **产品定位**

传统 PRD 的基本板块。

### **产品定义**

DeerFlow 是一款基于大语言模型的智能深度研究助手，通过多 Agent 协作系统，自动化完成"需求理解 → 计划制定 → 信息收集 → 分析整理 → 报告生成"的完整研究流程。

### **核心价值**

1. 1. **自动化研究流程**: 用户只需提出研究主题，系统自动完成全流程
    
2. 2. **多维度信息整合**: 整合网络搜索、网页爬取、私域知识库、代码执行等多种信息源
    
3. 3. **专业报告输出**: 生成结构化、引用规范的专业研究报告
    
4. 4. **人机协作模式**: 关键节点支持人工介入审核和调整
    

### **产品差异化**

|   |   |   |   |
|---|---|---|---|
|对比维度|传统搜索引擎|AI问答助手|DeerFlow|
|信息深度|浅层碎片信息|单轮问答，缺乏系统性|多步骤深度挖掘|
|信息整合|需用户手动整理|简单汇总|结构化报告输出|
|研究计划|无|无|自动生成可调整的研究计划|
|信息来源|单一网络搜索|训练数据+简单搜索|网络+爬虫+代码+知识库|
|人工控制|全人工|无法干预|关键节点可人工审核|

|   |   |   |
|---|---|---|
||传统方案局限性|大模型优势|

|多模态内容生成能力方面|单一文本内容格式输出缺乏创意和多样性内容创作成本高|支持文本、音频、图像等多种模态创意内容生成和风格化处理批量内容生产，降低成本跨模态内容一致性保证|

## 模型故事

此版块细描述 DeerFlow 中每个 Agent 的需求，帮助开发团队理解需要为每个 Agent 提供什么。

在传统PRD中，通过"用户故事"来描述用户需求:

- **在** [使用场景]下
    
- **为了** [达成目标]
    
- **需要** [功能支持]
    

在AI产品PRD中，需要编写"模型故事"来描述Agent需求:

- **作为** [Agent角色]
    
- **在** [任务场景]下
    
- **为了** [完成目标]
    
- **需要** [上下文信息/工具/能力支持]
    

  

### **Coordinator Agent 模型故事**

#### **模型故事1: 识别用户意图**

**场景描述**

当用户发送第一条消息时，我需要快速判断这是简单对话、不当请求还是研究请求。

**模型故事**

```Plain
作为 Coordinator Agent
在 接收到用户首次输入时
为了 正确分类并采取对应行动(直接回复/拒绝/移交)
我需要:

【上下文信息】
- 用户的原始输入文本
- 当前对话的语言locale(如果能检测到)
- 系统当前时间

【能力支持】
- 多语言理解能力(支持中英文等主流语言)
- 意图分类能力(三分类:问候/不当/研究)
- 工具调用能力(能主动调用handoff_to_planner工具)

【工具清单】
1. handoff_to_planner(research_topic， locale)
   - 用途: 将研究任务移交给Planner
   - 何时使用: 识别到研究请求时

【约束条件】
- 不能尝试直接回答研究问题
- 对于研究请求必须调用工具，不能文本回复
- 需要在3秒内完成意图识别
```

**为什么需要这些**

- **无历史对话**: 首次对话时没有上下文，需要单独依赖输入文本
    
- **快速决策**: 不需要深度思考，只需要快速分类
    
- **强制动作**: 通过工具绑定确保模型执行正确动作而非自由发挥
    

  

#### **模型故事2: 引导澄清对话**

**场景描述**

当用户提出模糊研究主题(如"研究AI"、"分析市场")时，我需要通过多轮对话获取明确的研究维度。

**模型故事**

```Plain
作为 Coordinator Agent
在 检测到用户研究主题过于模糊时
为了 通过最多3轮对话获取2+个明确维度

我需要:

【上下文信息】
- 用户的原始模糊主题
- 已经进行的澄清轮数(clarification_rounds)
- 历史澄清对话记录(clarification_history)
- 最大澄清轮数限制(max_clarification_rounds)
- 已识别的维度(从历史中提取)

【能力支持】
- 识别模糊程度的能力(判断是否需要澄清)
- 维度分析能力(知道研究需要哪些维度:技术/领域/角度/范围)
- 问题生成能力(生成聚焦特定维度的澄清问题)
- 防重复能力(不重复问已问过的维度)

【工具清单】
1. handoff_after_clarification(locale)
   - 用途: 澄清完成后移交给Planner
   - 何时使用: 已获得2+维度或达到最大轮数时

【约束条件】
- 每轮只问1个问题
- 每个问题必须聚焦不同维度
- 必须提供3-5个具体示例选项
- 不能问开放式问题(如"还有什么想了解的?")
- 第3轮后必须调用移交工具，不能继续问
```

  

**为什么需要这些**

- **渐进式信息收集**: 不能一次问太多，需要逐步引导
    
- **防止死循环**: 必须有轮数限制和强制退出机制
    
- **维度互补**: 每轮问题需要基于已有信息，问不同维度
    
- **用户友好**: 提供选项降低用户输入成本
    

  

#### **模型故事3: 处理澄清回复**

**场景描述**

在澄清过程中，用户给出了回复，我需要判断是否已获得足够信息，决定继续问还是移交。

**模型故事**

```Plain
作为 Coordinator Agent
在 收到用户对澄清问题的回复时
为了 决定是继续澄清还是移交给Planner
我需要:

【上下文信息】
- 原始模糊主题
- 所有历史澄清问答(包含本轮)
- 当前轮次(clarification_rounds)
- 从历史中提取的已明确维度列表

【能力支持】
- 信息提取能力(从用户回复中提取关键信息)
- 维度评估能力(判断已获得几个维度)
- 充分性判断能力(判断2+维度是否达成)

【决策规则】
- 0-1个维度: 继续问(生成新问题)
- 2+个维度: 调用handoff_after_clarification
- 达到最大轮数: 强制调用handoff_after_clarification

【约束条件】
- 必须准确统计维度数量
- 不能因为用户回复详细就误判为已充分
- 必须遵守轮数限制
```

**为什么需要这些**

- **客观评估**: 需要基于规则(维度数量)而非主观感觉
    
- **防止过早移交**: 用户说了很多但可能只覆盖1个维度
    
- **防止过度澄清**: 达到3轮必须停止，避免用户厌烦
    

  

### **Planner Agent 模型故事**

#### **模型故事1: 评估上下文充足性**

**场景描述**

接收到研究主题后，我需要首先评估:基于当前对话和背景信息，是否已经可以直接回答用户问题，无需额外搜索。

**模型故事**

```Plain
作为 Planner Agent
在 收到研究主题和背景信息时
为了 避免不必要的信息收集，快速响应简单问题
我需要:

【上下文信息】
- 用户的完整研究主题(可能经过澄清)
- 背景调查结果(如果启用了background_investigation)
- 对话历史(可能包含用户已提供的信息)
- 我的训练知识(通用知识储备)

【能力支持】
- 问题复杂度评估能力
- 信息覆盖度评估能力(现有信息是否能完整回答)
- 时效性判断能力(问题是否需要最新信息)

【评估标准】(需要非常严格)
满足以下ALL条件才能判断为"充足":
1. 当前信息能完整回答用户问题的所有方面
2. 信息来源可靠且最新
3. 没有显著的信息缺口
4. 数据有充分证据支撑
5. 覆盖了事实数据和必要背景
6. 信息量足以生成全面报告

任何一条不满足 → has_enough_context = false

【输出要求】
- 输出Boolean值: has_enough_context
- 如果true: 直接生成thought和title，不生成steps
- 如果false: 进入计划分解流程
```

**为什么需要这些**

- **避免浪费**: 对于简单问题(如"什么是Python?")，无需搜索
    
- **严格标准**: 必须非常严格，默认倾向"不充足"，避免信息不全
    
- **边界清晰**: 需要明确的评估标准，不能主观判断
    

  

#### **模型故事2: 分解研究任务**

**场景描述**

评估发现上下文不充足后，我需要将研究主题分解为3-5个可执行的步骤，每个步骤明确要收集什么信息。

**模型故事**

```Plain
作为 Planner Agent
在 确定需要收集更多信息时
为了 生成一个结构化、可执行的研究计划
我需要:

【上下文信息】
- 研究主题(明确的，可能经过澄清)
- 背景调查结果(快速搜索的摘要)
- 最大步骤数限制(max_step_num，如3或5)
- 语言locale(决定输出语言)

【能力支持】
- 任务分解能力(将大主题拆成子任务)
- 全面性思考能力(覆盖多个分析维度)
- 逻辑排序能力(步骤应该有合理顺序)
- 数据需求定义能力(明确每步要收集什么)

【思考框架】(8个维度引导)
在分解任务时，考虑以下维度:
1. 历史背景(如果需要)
2. 当前状况(主要)
3. 未来趋势(如果相关)
4. 利益相关方(如果适用)
5. 定量数据(数字、统计)
6. 定性信息(观点、案例)
7. 对比分析(如果需要)
8. 风险和挑战(如果重要)

不是每个主题都需要所有维度，根据实际情况选择最重要的3-5个方面。

【步骤类型判断】
每个步骤需要标记:
- need_search: true → 需要网络搜索、爬取、知识库检索
  - 示例: 收集市场数据、查找新闻、获取趋势
- need_search: false → 不需要搜索，只需要数据处理
  - 示例: 计算、API调用、代码执行

【输出要求】
生成严格符合以下schema的JSON:
{
  "locale": "zh-CN"，
  "has_enough_context": false，
  "thought": "重述用户需求，说明为什么需要这些步骤"，
  "title": "研究计划标题"，
  "steps": [
    {
      "title": "步骤标题"，
      "description": "具体要收集什么数据，从哪些角度"，
      "need_search": true，
      "step_type": "research"
    }
  ]
}

【约束条件】
- 步骤数量: 不超过max_step_num
- 每步要具体: 不能说"收集信息"，要说"收集2024年销量数据"
- 步骤互不重叠: 不同步骤聚焦不同方面
- 有逻辑顺序: 通常先基础再深入
- 不包含总结步骤: 不要加"汇总分析"这样的步骤
```

**为什么需要这些**

- **结构化输出**: 必须是JSON，不能是自由文本，便于程序处理
    
- **可执行性**: 每个步骤都要能被Researcher/Coder执行
    
- **全面性**: 8维度框架防止遗漏重要方面
    
- **步骤限制**: 控制在3-5步，平衡全面性和效率
    

  

#### **模型故事3: 处理用户反馈**

**场景描述**

生成计划后，用户可能提出修改意见(如"删除第2步"、"增加成本分析")，我需要理解反馈并生成新计划。

**模型故事**

```Plain
作为 Planner Agent
在 收到用户对计划的修改意见时
为了 生成符合用户期望的新计划
我需要:

【上下文信息】
- 原始研究主题
- 之前生成的计划(包含所有步骤)
- 用户的反馈内容
- 当前迭代轮次(plan_iterations)
- 最大迭代次数限制

【能力支持】
- 反馈理解能力(理解用户要删除/增加/修改什么)
- 计划调整能力(基于反馈修改步骤)
- 逻辑一致性保持能力(修改后计划仍然合理)

【常见反馈类型】
1. 删除步骤: "去掉第X步" → 删除对应步骤
2. 增加内容: "增加XX分析" → 新增步骤或修改现有步骤
3. 修改重点: "更关注XX方面" → 调整步骤的description
4. 调整顺序: "先XX再YY" → 重新排序
5. 缩减范围: "只要XX，不要YY" → 简化计划

【约束条件】
- 必须响应用户反馈，不能忽略
- 修改后仍要符合JSON schema
- 仍要遵守步骤数量限制
- 如果达到最大迭代次数，不再重新规划
```

**为什么需要这些**

- **用户控制权**: 用户是"决策者"，有权修改作战计划
    
- **理解意图**: 用户反馈可能不规范，需要理解真实意图
    
- **防止死循环**: 必须有迭代次数限制
    

  

### **Researcher Agent 模型故事**

#### **模型故事1: 执行网络搜索步骤**

**场景描述**

接收到一个需要网络搜索的研究步骤，我需要确定搜索关键词、执行搜索、可能爬取页面、整理信息、提供引用。

**模型故事**

```Plain
作为 Researcher Agent
在 执行一个need_search=true的研究步骤时
为了 收集全面、准确、有引用来源的信息
我需要:

【上下文信息】
- 当前步骤的title和description(明确要收集什么)
- 已完成步骤的发现(避免重复，形成递进)
- 研究主题(整体背景)
- 语言locale(决定搜索语言)

【工具清单】
1. web_search(query: str)
   - 用途: 网络搜索
   - 返回: 搜索结果列表(title， url， snippet， images)
   - 何时使用: 首先使用，获取初步信息

2. crawl_tool(url: str)
   - 用途: 深度爬取页面全文
   - 返回: 页面完整内容
   - 何时使用: 当搜索结果snippet不够详细，且url可靠时

3. local_search_tool(query: str) [如果用户提供了知识库]
   - 用途: 检索私域知识库
   - 何时使用: 优先于web_search使用

4. 其他动态加载的MCP工具(如有)
   - 根据配置动态出现
   - 可能包括: 特殊搜索、数据库查询等

【执行流程】
1. 理解步骤需求 → 明确要收集什么信息
2. 构造搜索关键词 → 可能需要多个搜索词覆盖不同角度
3. 执行搜索 → 调用web_search或local_search_tool
4. 评估结果 → 判断是否需要爬取页面
5. 爬取内容(可选) → 对关键URL调用crawl_tool
6. 整合信息 → 汇总搜索结果和爬取内容
7. 去重和质量过滤 → 去除重复或低质量信息
8. 记录来源 → 追踪每条信息的URL

【能力支持】
- 关键词生成能力(从步骤描述提取搜索词)
- 信息筛选能力(从海量结果中选取相关信息)
- 去重能力(识别重复信息)
- 来源追踪能力(记住每条信息来自哪个URL)
- 多工具协调能力(决定何时用哪个工具)

【输出要求】
Markdown格式，包含:
- ## Problem Statement: 重述步骤需求
- ## Research Findings: 按主题组织的发现(不含内联引用)
- ## Conclusion: 本步骤的总结
- ## References: URL列表，格式为 `- [Title](URL)` + 空行

【约束条件】
- 不依赖训练数据: 必须调用工具，不能用旧知识
- 不做计算: 遇到计算需求，说明需要Coder
- 不编造来源: 引用的URL必须真实
- 不重复已有发现: 要形成递进，不能重复前面步骤的内容
```

**为什么需要这些**

- **工具多样性**: 不同任务需要不同工具，必须会选择
    
- **信息追溯**: 最终报告需要引用，必须记录来源
    
- **质量控制**: 网络信息质量参差，需要筛选
    
- **递进关系**: 多个步骤之间应该形成递进，不是简单罗列
    

  

#### **模型故事2: 时间范围限制的搜索**

**场景描述**

步骤描述中包含时间范围(如"2024年的市场数据"、"最近三年的趋势")，我需要确保搜索结果符合时间要求。

**模型故事**

```Plain
作为 Researcher Agent
在 步骤描述包含时间要求时
为了 确保收集的信息符合时间范围
我需要:

【上下文信息】
- 步骤中的时间表述(如"2024年"、"近三年"、"最新")
- 当前系统时间(用于计算相对时间)

【能力支持】
- 时间表述识别能力(从描述中提取时间要求)
- 搜索参数构造能力(加入时间限制)
- 结果时间验证能力(检查结果的发布时间)

【处理策略】
1. 绝对时间: "2024年" → 搜索时加入"2024"关键词，验证结果日期
2. 相对时间: "最近一年" → 基于当前时间计算，搜索时加入时间参数
3. 最新信息: "最新" → 优先选择最近发布的结果

【约束条件】
- 必须验证时间: 不能只看标题，要检查发布日期
- 明确说明: 如果找不到指定时间的信息，需要在结论中说明
```

**为什么需要这些**

- **时效性要求**: 很多研究问题对时间敏感
    
- **准确性**: 用错时间的数据会导致错误结论
    
- **透明性**: 如果信息缺失，需要告知
    

  

### **Coder Agent 模型故事**

#### **模型故事: 执行数据处理步骤**

**场景描述**

接收到一个need_search=false的步骤，可能需要编写Python代码进行计算、数据处理、API调用等。

**模型故事**

```Plain
作为 Coder Agent
在 执行一个need_search=false的数据处理步骤时
为了 通过代码完成计算或数据操作
我需要:

【上下文信息】
- 当前步骤的title和description
- 已完成步骤的数据和发现(可能包含需要处理的数据)
- 研究主题

【工具清单】
1. python_repl_tool(code: str)
   - 用途: 执行Python代码
   - 运行环境: 沙箱，有基础库(numpy， pandas等)
   - 返回: 执行结果或错误信息

2. 其他动态MCP工具(如有)
   - API调用工具
   - 数据库查询工具
   - 等

【能力支持】
- 代码编写能力(Python)
- 问题分析能力(理解需要什么计算)
- 调试能力(处理执行错误)
- 结果解释能力(解释计算结果的意义)

【执行流程】
1. 理解需求 → 明确要计算/处理什么
2. 编写代码 → 生成Python代码
3. 执行代码 → 调用python_repl_tool
4. 处理错误(如果有) → 调试并重新执行
5. 解释结果 → 说明计算结果的含义

【输出要求】
Markdown格式，包含:
- ## Problem Statement: 重述步骤需求
- ## Approach: 说明采用的方法
- ## Code and Results: 代码和执行结果
- ## Analysis: 对结果的分析解释

【约束条件】
- 代码必须可执行: 不能有伪代码
- 处理错误: 执行失败要尝试修复
- 安全考虑: 不能执行危险操作(如文件删除)
- 解释清楚: 代码和结果都要有注释/说明
```

**为什么需要这些**

- **能力互补**: Researcher做不了计算，需要Coder
    
- **沙箱环境**: 代码执行有风险，需要隔离环境
    
- **可解释性**: 不能只给代码和数字，要解释意义
    

  

### **Reporter Agent 模型故事**

#### **模型故事1: 汇总生成报告**

**场景描述**

所有研究步骤完成后，我需要将各步骤的发现汇总成一份结构化、引用规范、风格统一的研究报告。

**模型故事**

```Plain
作为 Reporter Agent
在 收到所有研究步骤的发现后
为了 生成一份专业的研究报告
我需要:

【上下文信息】
- 研究主题(title和thought)
- 所有步骤的发现(Markdown格式，包含引用)
- 报告风格(report_style: academic/popular_science/news等)
- 语言locale
- 当前时间

【能力支持】
- 信息整合能力(汇总多个步骤的发现)
- 结构化写作能力(按固定结构组织内容)
- 风格适配能力(根据report_style调整语言风格)
- 引用管理能力(从各步骤中提取并统一格式化引用)
- 图片整合能力(从步骤中提取图片并嵌入报告)

【内容来源原则】
- 只能使用: 步骤中已收集的信息
- 不能编造: 任何未在步骤中出现的信息
- 信息缺失时: 明确说明"信息未提供"
- 不确定时: 使用"可能"、"据XX显示"等表述

【报告结构】(6个部分，必须全部包含)
1. Title (一级标题)
2. Key Points (4-6个要点bullet list)
3. Overview (1-2段概述)
4. Detailed Analysis (多个二级标题，组织详细内容)
5. Survey Note (可选，深度分析部分)
6. Key Citations (所有引用列表)

【风格要求】(根据report_style)
- academic: 正式、严谨、第三人称、专业术语
- popular_science: 生动、类比、故事化、通俗易懂
- news: 倒金字塔、归因明确、客观中立
- social_media(中文): "姐妹们"、emoji、种草语言
- strategic_investment: 技术深度+投资建议、数据表格

【格式要求】
- 使用Markdown表格: 对比数据、特征列表等优先用表格
- 图片嵌入: `![描述](url)`，放在相关内容附近
- 引用格式: `- [Source Title](URL)` + 空行分隔
- 无内联引用: 正文中不出现[1][2]这样的标注

【约束条件】
- 不能超出步骤内容: 不添加未收集的信息
- 必须包含所有步骤的发现: 不能遗漏
- 引用必须准确: URL必须来自步骤中的References
- 结构必须完整: 6个部分都要有(Survey Note可选)
```

**为什么需要这些**

- **信息完整性**: 必须包含所有步骤，不能遗漏
    
- **防止幻觉**: 只能用已收集的信息，不能编造
    
- **风格适配**: 不同场景需要不同风格
    
- **引用规范**: 学术和专业报告必须有引用
    

  

#### **模型故事2: 长上下文管理**

**场景描述**

当研究步骤很多、每步发现都很详细时，所有内容加起来可能超出模型的上下文长度限制，我需要在不丢失关键信息的前提下完成报告。

**模型故事**

```Plain
作为 Reporter Agent
在 总上下文接近或超出模型限制时
为了 仍然生成完整报告
我需要:

【上下文信息】
- 所有步骤的发现(可能很长)
- 模型的token限制(如128k)
- 当前已使用的token数

【技术支持】
- 上下文压缩机制(ContextManager)
  - 自动压缩observation messages
  - 优先保留最新和最重要的信息
  - 保留关键数据和引用

【压缩策略】
1. 优先级排序: 最新步骤 > 历史步骤
2. 内容提取: 保留核心发现，去除冗余表述
3. 引用保留: 引用列表必须完整保留
4. 数据优先: 数字、表格等关键数据优先保留

【能力支持】
- 重要性判断能力(识别哪些内容最关键)
- 信息压缩能力(用更少文字表达同样意思)
- 完整性保持能力(压缩后仍然逻辑完整)
```

**为什么需要这些**

- **技术限制**: 模型有上下文长度限制
    
- **质量保证**: 不能因为压缩而丢失关键信息
    
- **自动化**: 不能让用户手动选择保留什么
    

  

### **Human Feedback 节点需求**

#### **场景描述**

这不是一个Agent，而是一个"人在环中"的决策节点，但仍需要定义它需要什么信息来支持人类决策。

#### **节点需求**

```Plain
作为 Human Feedback 节点
在 展示研究计划给用户审核时
为了 让用户能够快速理解计划并做出决策
我需要:

【展示信息】
- 研究主题(用户能回忆起自己的需求)
- 研究计划的thought(让用户理解AI的思路)

- 每步的need_search标记(让用户知道哪些步骤会联网)

【交互能力】
- 暂停工作流: 使用interrupt()机制暂停
```

- **控制权**: 用户是决策者，应该有修改权
    
- **效率平衡**: API场景支持自动接受，提高效率
    

  

⚠️ 模型故事版块以下两个子版块内容为解释性文字，非真实 PRD 所需内容

### **模型故事 vs 技术实现**

#### **重要说明**

模型故事描述的是"Agent需要什么"，而不是"如何实现"。这两者的对应关系:

|   |   |
|---|---|
|模型故事中的需求|对应的技术实现|
|上下文信息|State字段、消息历史、函数参数|
|工具清单|LangChain Tools、MCP工具、Function Calling|
|能力支持|模型选择(GPT-4/Claude等)、提示词设计|
|输出格式|Structured Output、JSON Schema、正则解析|
|约束条件|提示词约束、代码逻辑校验、重试机制|

#### **开发团队如何使用模型故事**

1. 1. **理解需求**: 先读模型故事，理解Agent到底需要什么
    
2. 2. **准备上下文**: 确保State中包含模型故事中要求的所有上下文信息
    
3. 3. **配置工具**: 根据工具清单，绑定对应的工具到Agent
    
4. 4. **选择模型**: 根据能力要求，选择合适的LLM(如复杂推理用Claude Sonnet)
    
5. 5. **设计提示词**: 基于约束条件和输出要求，编写提示词
    
6. 6. **实现校验**: 添加代码逻辑确保输出符合约束
    

  

### **总结:模型故事的核心价值**

#### **对产品经理**

- ✅ 清晰表达Agent需求，类似传统PRD中的用户故事
    
- ✅ 帮助思考Agent的能力边界和依赖
    
- ✅ 为评估技术可行性提供依据
    

#### **对开发团队**

- ✅ 明确每个Agent需要哪些输入
    
- ✅ 知道需要配置哪些工具
    
- ✅ 理解输出格式和约束条件
    
- ✅ 指导提示词设计和代码实现
    

#### **对测试团队**

- ✅ 理解测试时需要准备哪些上下文数据
    
- ✅ 知道如何构造测试用例
    
- ✅ 了解预期的输出格式

## 用户旅程

#### **阶段1：问题输入与初步理解（0-2分钟）**

- 用户访问DeerFlow平台
    
- 输入研究问题或选择预设问题
    
- 系统展示欢迎界面和功能说明
    

**系统响应**：

- 协调器接收用户输入
    
- 进行语言检测和意图识别
    
- 判断是否需要澄清对话
    

**关键交互点**：

- 自然语言输入框
    
- 内置问题选择器
    
- 语言选择（中英文）
    

**用户体验目标**：

- 降低使用门槛，支持自然语言交互
    
- 提供引导，帮助用户明确需求
    

  

#### **阶段2：智能澄清与需求确认（2-5分钟）**

**用户行为**：

- 用户回答澄清问题
    
- 多轮对话确认具体需求

- 澄清进度显示
    

**用户体验目标**：

#### **阶段3：研究计划制定与确认（5-8分钟）**

## **Agent 旅程设计**

### **传统用户旅程 vs Agent 工作流**

在传统产品中，会绘制"用户旅程图"，描述用户如何一步步操作系统。

但在 AI 产品中，用户只是在关键节点进行决策，大部分执行工作由 Agent 完成。

因此，我们需要将**用户旅程转变为 Agent 工作流**。

  

在 Agent 工作流中:

- **用户**: 提出需求，在关键节点做决策
    
- **Agent**: 理解需求，执行具体任务，汇报结果

## **测试标准**

传统软件产品的测试是"确定性"的:输入A必然得到输出B。

但AI产品的测试是"概率性"的:输入A可能得到多种合理的输出。因此需要制定不同的测试标准。

### **功能测试标准**

#### **Coordinator 测试**

|   |   |   |   |
|---|---|---|---|
|测试场景|测试方法|通过标准|测试用例量|
|意图分类准确性|准备100个输入样本，人工标注正确分类，测试模型预测|准确率 ≥ 95%|100|
|澄清问题质量|对20个模糊主题，评估生成的澄清问题是否聚焦不同维度|维度覆盖度 ≥ 2不重复率 100%|20|
|澄清轮数控制|测试是否在3轮内完成澄清或强制移交|100%在3轮内结束|50|
|不当请求拒绝|测试对prompt泄露、有害内容等请求的拒绝能力|拒绝率 100%|30|

## **异常处理与降级策略**

### **异常场景定义**

|   |   |   |   |
|---|---|---|---|
|异常场景|触发条件|用户感知|降级策略|
|LLM响应超时|单次调用超过60s|提示"思考中，请稍候"|重试1次仍超时则返回部分结果|
|LLM返回格式错误|JSON解析失败|提示"理解出错，正在重试"|尝试JSON修复重新调用失败则跳过该步骤|
|搜索引擎故障|搜索API返回错误|提示"搜索服务异常"|切换备用搜索引擎仍失败则跳过该步骤|
|网页爬取失败|爬虫返回403/404等|无感知，继续其他步骤|仅记录日志，不影响流程|
|Token超限|上下文超出模型限制|提示"信息过多，正在压缩"|触发上下文压缩优先保留最新信息|
|用户澄清超时|等待用户回复超过5分钟|提示"已自动继续"|基于已有信息继续执行|
|计划审核超时|等待用户审核超过10分钟|提示"已自动接受计划"|自动接受当前计划并执行|
|全部步骤失败|所有研究步骤都失败|提示"暂时无法完成研究"|返回错误信息，建议用户重试|

## **PRD撰写说明**

  

本节仅用于教学目的，实际PRD中不应包含此部分

### **本PRD与传统PRD的区别**

|   |   |   |
|---|---|---|
|区别点|传统PRD|本PRD(AI产品)|
|核心流程|用户旅程图|Agent工作流图|
|功能描述|页面+交互+逻辑|Agent角色+任务+输入输出|
|关键章节|界面原型|提示词设计策略（原型图同样重要，或许未来可以被 Dify 替代）|
|新增章节|-|评估数据集要求、测试标准|

### **提示词章节的重要性**

在AI产品PRD中，"提示词设计"章节是核心，但**不应**直接交付提示词，而是:

1. 1. **设计思考**: 为什么这样设计?要解决什么问题?
    
2. 2. **策略说明**: 采用了哪些策略(COT/Few-shot/工具绑定)?
    
3. 3. **输出控制**: 如何控制模型输出符合预期?
    
4. 4. **示例说明**: 用示例解释设计意图
    

  

### **与真实项目的对应关系**

本PRD是基于已完成的DeerFlow项目"倒推"出来的，在真实场景中:

1. 1. **PRD先于开发**: 产品经理先写PRD → 开发团队实现
    
2. 2. **本文是反向**: 先有实现 → 撰写PRD用于教学
    

因此，真实PRD撰写时:

- 提示词章节只有"设计策略"，完整提示词部分应该是待迭代的初稿，文档中使用了真实项目提示词的中文翻译稿
    
- 测试标准是"预期目标"，而非"已达成指标"
    
- 数据集要求是"待收集"，而非"已有数据"
