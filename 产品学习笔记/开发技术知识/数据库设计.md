## 第一讲 认知破局：为什么产品经理必须懂数据库？

很多同学会问：我一个PM，画好原型、写好PRD就够了，为什么要懂数据库？我先给大家讲透**一个核心结论**：**产品功能的本质，是数据的流转和呈现；数据库设计，就是产品功能的底层骨架。骨架搭错了，你设计的功能就是空中楼阁，后期改动成本是前期的100倍。**

### 1.1 先看一个让无数PM踩坑的血泪案例

2021年，一位PM负责SaaS产品，上线3个月后，业务提了个看似“简单”的需求：一个账号可以属于多个公司，支持组织切换、不同组织独立数据权限。

这位PM觉得需求很简单，PRD里只写了两句交互规则，结果研发直接给了晴天霹雳：**现在的数据库设计，用户和组织是一对一绑定，要改多对多，需要重构100+张表，开发周期3个月**。

我们用大白话讲透为什么代价这么大：

- 错误设计：就像给每个员工做了一张工牌，工牌上只能印**一个公司ID**。这就意味着，一个员工永远只能属于一家公司。现在要支持一个人属于多家公司，等于要把全公司所有员工的工牌全部作废，整个工牌体系推翻重做，所有和工牌关联的门禁、考勤、薪酬系统全部要改。
    
- 正确设计：提前做一张「员工-公司关系表」。员工信息是一张表，公司信息是一张表，谁属于哪个公司、在公司里是什么角色，全在这张关系表里记录。要加一个新的公司归属，只需要在关系表里加一行记录，根本不用动原来的员工表、公司表。
    

这个案例给我们的教训，是所有PM必须刻在脑子里的：**你在设计产品功能的时候，本质上就是在设计数据模型。如果一开始没考虑数据的扩展性，后续业务的任何一点变化，都可能带来毁灭性的改造成本。**

### 1.2 数据库设计，直接决定你产品的3个核心命脉

很多同学觉得数据库影响的只是技术，和产品无关，大错特错。它直接决定了你产品的生死：

1. **功能能不能做**
    

2. 好的设计：新增需求改代码就行，1周上线；
    

3. 差的设计：新增需求要重构数据库，1-3个月，甚至根本做不了。
    

4. **性能好不好**
    

5. 最典型的例子：订单表100万条数据，用户查自己的订单要3秒，用户直接就流失了。根因不是前端卡，是订单表的user_id字段没加索引；加了索引之后，查询只需要50ms，体验天差地别。
    

6. **成本高不高**
    

7. 不合理的设计：查询慢，只能靠加服务器解决，10台服务器还卡，公司成本直线上升，你的项目预算直接被砍；
    

8. 合理的设计：1台服务器就能支撑，成本可控，项目才有持续迭代的空间。
    

### 1.3 懂数据库的PM，和不懂的PM，职场差距有多大？

我给大家做个直观的对比，你看看自己属于哪一类：

|工作场景|不懂数据库的PM|懂数据库的PM|
|---|---|---|
|需求评审提需求|张口就来“这个功能很简单吧，3天够不够？”|提前说明“这个需求涉及表结构变更，咱们先评估影响范围，看看能不能先做MVP”|
|研发说工期长被质疑|只会反问“为什么这么慢？是不是你们技术能力不行？”|立刻理解“这涉及数据迁移和兼容，我们一起讨论下最优方案”|
|产品设计阶段|只画原型，完全不关心数据模型，上线再说|提前画ER图，考虑数据扩展性，提前规避性能和改造成本|
|线上出性能问题|只会催研发“快点优化，用户投诉了”|能和研发一起定位“是不是这个查询场景没加索引？能不能用冗余优化？”|

一句话总结：**懂数据库的****PM****，是和研发并肩作战的业务伙伴；不懂的PM，只会给研发提需求的“原型工具人”。**

## 第二讲 选型入门：3种主流数据库，到底该怎么选？

很多同学对数据库的认知，只停留在“MySQL”这三个字上。实际业务中，我们不会只用一种数据库，不同的数据、不同的场景，要选对应的数据库，才能兼顾性能、成本和扩展性。

我们先给大家讲透3种最核心的数据库，用大白话讲清“是什么、什么时候用、有什么坑”。

### 2.1 关系型数据库MySQL：产品核心业务的“保险柜”

#### 是什么？

你可以把MySQL理解成一个**结构化的Excel工作簿**：

- 一个数据库就是一个Excel文件，里面有很多张表（对应Excel的sheet）；
    
- 每张表有固定的列（字段），每一行是一条数据；
    
- 表和表之间，可以通过共同的字段建立关联关系（比如用户表的用户ID，关联订单表的用户ID，就能找到这个用户的所有订单）。
    

#### 核心优势

1. 支持**事务**：简单说，就是能保证“操作要么全成功，要么全失败”。比如用户下单，扣库存、扣钱、生成订单，这三个步骤必须同时成功，不能钱扣了订单没生成，这个只有MySQL能稳定保证。
    
2. 支持复杂查询：多表关联、数据统计、聚合分析，功能极强。
    
3. 成熟稳定，生态完善，开源免费，几乎是所有业务系统的标配。
    

#### 适用场景（必记）

所有**结构固定、关系明确、需要保证数据准确性**的核心业务数据，比如：用户信息、订单、商品、库存、支付记录等。

### 2.2 非关系型数据库MongoDB：灵活数据的“文件夹”

#### 是什么？

你可以把MongoDB理解成一个**放****JSON****文件的文件夹**：

- 每个数据是一个独立的JSON文档，不用固定列，每个文档里的字段可以不一样；
    
- 比如用户画像数据，有的用户有10个标签，有的有100个，有的有地址信息，有的没有，用MySQL要加无数列，用MongoDB每个用户的文档自己想加什么就加什么，完全灵活。
    

#### 核心优劣势

- 优势：Schema完全灵活，不用提前设计表结构，水平扩展方便，适合存海量的非结构化数据；
    
- 劣势：不支持复杂的多表查询，事务支持弱，不适合存核心交易数据。
    

#### 适用场景（必记）

**数据结构不固定、字段经常变、读多写少**的场景，比如：用户画像、操作日志、行为数据、动态表单数据等。

### 2.3 缓存数据库Redis：高频数据的“随手抽屉”

#### 是什么？

你可以把Redis理解成你办公桌的**随手抽屉**，而MySQL是办公室的文件柜：

- 文件柜存的东西多、安全，但是拿取慢；随手抽屉只放你每天都要用的东西，伸手就能拿到，速度极快。
    
- Redis的数据存在内存里，读写速度是微秒级，比MySQL快几百上千倍；但内存成本高，不能存大量数据，断电可能丢失。
    

#### 核心优劣势

- 优势：读写超快，支持丰富的数据结构，能做计数器、排行榜、分布式锁等；
    
- 劣势：内存成本高，不能存海量冷数据，不适合做持久化存储。
    

#### 适用场景（必记）

**高频读取、低写入、需要极致性能**的场景，比如：首页热点数据、用户登录信息、商品库存计数、点赞数/浏览量、排行榜、分布式锁等。

### 2.4 选型终极判断标准+实战组合

#### 3个问题，10秒选对数据库

1. 数据有没有明确的关联关系？要不要保证交易/操作的准确性？→ 是，选MySQL
    
2. 是不是高频读取的热点数据？要不要极致的读写速度？→ 是，选Redis
    
3. 数据结构是不是不固定、经常变？是不是海量非结构化数据？→ 是，选MongoDB
    

#### 实际项目的标准组合用法

几乎所有成熟的业务系统，都是三者组合使用，各司其职：

- **MySQL**：存核心业务数据（用户、订单、商品、支付），是系统的根基；
    
- **Redis**：缓存热点数据（首页推荐、用户登录态、商品库存），扛住高并发查询；
    
- **MongoDB**：存日志、行为数据、用户画像，承接海量非结构化数据。

## 第三讲 核心技能：表结构设计的5个黄金原则

这一讲是本节课的核心，也是产品经理最能落地、最能直接产生价值的部分。表结构设计，就是产品数据模型的落地，你掌握了这5个原则，就能在需求设计阶段，提前规避90%的坑。

### 原则1：字段命名要见名知意，规范统一

这个原则看似基础，却是无数团队踩过的坑。就像你给原型里的按钮命名，不能叫button1、button2，否则过一个月连你自己都不知道是什么意思。

#### 错误示范

建了一张表，字段叫f1、f2、f3，没有任何注释，别说产品，过一个月研发自己都忘了这个字段是干嘛的，后续改需求、排查问题，全是雷。

#### 正确规范（所有PM必须记下来，写PRD要按这个来）

1. 表名/字段名：全部小写+下划线，比如用户订单表叫`user_orders`，用户ID字段叫`user_id`，禁止拼音、缩写、大小写混写；
    
2. 必须加COMMENT注释：每个表、每个字段都要写清楚是干嘛的，状态字段必须写清枚举值，比如`status TINYINT COMMENT '状态:1-正常,2-禁用'`；
    
3. 必须有通用基础字段：`id`（主键）、`created_at`（创建时间）、`updated_at`（更新时间），这三个字段是所有表的标配。
    

### 原则2：合理的主键设计

主键，就是表里每一行数据的**唯一身份证号**，就像每个人的身份证号，全局唯一，不会重复，是所有数据关联的核心。

我们给大家讲透3种主流主键方案，以及什么时候用：

|主键方案|核心特点|优点|缺点|适用场景|
|---|---|---|---|---|
|自增ID|1、2、3、4...按顺序自增|简单、性能好、占用空间小|分库分表会出现ID重复，对外暴露会泄露业务数据量|单库单表的小项目，不对外暴露的内部表|
|UUID|随机生成的全局唯一字符串|全局唯一，不会重复|无序、占用空间大、索引性能差|对外暴露的ID，比如给第三方对接的用户ID|
|雪花ID（推荐）|64位结构化ID，包含时间戳+机器ID+序列号|全局唯一、有序递增、性能好、自带时间信息|弱依赖系统时钟|分布式系统、中大型项目，所有核心业务表的首选|

给PM的核心建议：**核心业务表，优先用雪花ID做为主键**，既能保证全局唯一，又能兼顾性能，还能避免自增ID泄露业务数据量的问题。

### 原则3：适度的表拆分

很多同学觉得，表的字段越多越好，所有相关数据都放一张表里，省得关联查询。大错特错，表的字段太多、数据量太大，会导致查询速度直线下降，必须做适度拆分。

拆分分两种，垂直拆分和水平拆分，我们分别讲透：

#### 1. 垂直拆分：按字段的使用频率拆分

你可以理解成：把衣柜分成「常穿区」和「不常穿区」，常穿的衣服放最顺手的层板，不常穿的放顶柜。

- 错误设计：用户表有50多个字段，登录要查的用户名、邮箱，和不常用的头像、个人简介、个性化设置全放一张表里。每次用户登录，都要查全表50多个字段，速度极慢。
    
- 正确设计：
    
    - 主表`users`：只放高频使用的基础字段（用户ID、用户名、邮箱、状态、创建时间），每次查询只扫少量数据，速度飞快；
        
    - 扩展表`user_profiles`：放低频使用的字段（头像、简介、个性化设置），用用户ID关联，只有用户进入个人中心的时候才会查询。
        

**拆分时机**：单表字段超过20个，就要考虑垂直拆分。

#### 2. 水平拆分：按数据量拆分

你可以理解成：档案柜里的文件，按年份分盒子，2024年的放一个盒子，2025年的放另一个，找文件的时候不用翻所有档案。

最典型的场景就是订单表：日增1万单，一年就是365万，3年就超过1000万条数据，全放一张表里，查询会越来越慢。

- 正确设计：按月分表，`orders_202401`、`orders_202402`、`orders_202403`，查哪个月的订单，就去对应的表里查，速度提升几十倍。
    

**拆分时机**：单表数据量超过1000万条，或者查询性能明显下降，就要考虑水平拆分。

给PM的核心建议：**设计产品的时候，就要提前预估数据量**。比如订单系统，日增1万单，3年就破千万，提前就要考虑分表方案，不要等数据爆了再改，成本极高。

### 原则4：必要的冗余设计

很多同学听过“数据不能冗余，要保证唯一性”的说法，但在实际业务中，**适度的冗余，是提升性能、适配业务的核心手段**。

我们用最常见的场景举例：订单列表需要显示下单用户的用户名。

- 方案1：不冗余，纯关联查询
    

订单表只存`user_id`，每次查订单列表，都要关联用户表，去查对应的用户名。如果订单表有100万条数据，每次查询都要关联两个大表，速度极慢。

- 方案2：冗余设计，订单表直接存`username`
    

下单的时候，直接把用户名冗余存到订单表里，查订单列表的时候，直接查订单表就能拿到所有数据，不用关联，速度提升几百倍。

#### 冗余设计的利弊

- 好处：① 查询速度极快，不用多表关联；② 数据独立，用户后续改了用户名，历史订单里的用户名还是下单时的，完全符合业务逻辑。
    
- 代价：① 占用少量存储空间；② 存在数据一致性问题（需要判断要不要同步更新）。
    

#### 什么时候用冗余？（3个必备条件，同时满足）

1. 读多写少的场景（比如订单、日志，生成后几乎不会修改）；
    
2. 多表关联查询慢，严重影响性能；
    
3. 历史数据不需要同步更新。
    

给PM的核心建议：设计列表页、详情页的时候，先想清楚“这个字段是不是高频查询、会不会经常修改”，如果符合冗余条件，就可以主动和研发提冗余设计，大幅提升页面性能。

### 原则5：预留扩展字段

互联网业务的特点就是变化快，今天加个订单来源，明天加个渠道ID，后天加个活动编号。如果每次加字段都要改表结构，在MySQL里，大表改结构会锁表，甚至导致业务停服，风险极高。

所以，设计表的时候，一定要提前预留扩展字段，给业务变化留后路：

- 基础扩展字段：`ext_field1`、`ext_field2`、`ext_field3`，VARCHAR类型，存简单的文本信息；
    
- 灵活扩展字段：`ext_json`，JSON类型，能存结构化的动态数据，比如订单来源、渠道、活动ID等，不用改表结构，就能支持临时新增的需求。
    

给PM的核心建议：写PRD的时候，遇到不确定的、临时的、迭代快的需求，优先考虑用扩展字段实现，不用大动干戈改表结构，大大缩短开发周期，降低线上风险。

## 第四讲 性能优化：索引，让你的查询快100倍

80%的线上性能问题，都是索引没做好。这一讲，我们不讲复杂的算法，只讲产品经理能听懂、能用到的索引核心知识，让你以后再遇到“页面加载慢”的问题，能直接找到根因。

### 4.1 什么是索引？大白话讲透

索引，就是**数据库的目录**。

- 没有索引：你想找一本书里的“数据库设计”章节，没有目录，只能从第一页翻到最后一页，遍历整本书，这就是「全表扫描」；
    
- 有索引：你直接看目录，找到这个章节在第100页，直接翻过去，几秒钟就找到了，这就是「索引查询」。
    

回到文章里的案例：订单表100万条数据，查某个用户的订单，没有索引要遍历100万条数据，耗时3秒；给`user_id`加了索引之后，直接定位到目标数据，耗时50ms，性能提升60倍。

### 4.2 3种核心索引类型，重点讲透最容易踩坑的联合索引

#### 1. 单列索引

给单个字段建索引，比如给订单表的`user_id`建索引`idx_user_id`，只要查询条件里有`user_id`，就能用到这个索引，是最基础的索引类型。

#### 2. 联合索引（重点，PM必须吃透）

给多个字段一起建索引，比如给订单表的`(user_id, created_at)`建联合索引`idx_user_created`，是业务中最常用、也最容易踩坑的索引类型。

这里必须讲透**联合索引的最左匹配原则**，这是索引生效的核心规则：

联合索引就像查字典，你要查“张”这个字，必须先找声母`zh`，再找韵母`ang`，你不能跳过声母，直接找韵母`ang`，字典里根本没法查。

联合索引也是一样，索引是按从左到右的顺序排序的，查询的时候，**必须匹配最左边的字段，才能用到索引，跳过左边的字段，索引直接失效**。

举个例子，我们给订单表建了联合索引`(user_id, created_at, status)`：

- ✅ 生效：`where user_id = 123`（匹配最左字段）
    
- ✅ 生效：`where user_id = 123 and created_at > '2024-01-01'`（按顺序匹配前两个字段）
    
- ✅ 生效：`where user_id = 123 and created_at > '2024-01-01' and status = 1`（全字段匹配）
    
- ❌ 失效：`where created_at > '2024-01-01'`（跳过了最左的user_id）
    
- ❌ 失效：`where status = 1`（跳过了最左的user_id）
    

给PM的核心建议：**你设计产品的查询场景时，就要考虑联合索引的顺序**。比如用户最常用的场景是“查自己的订单，按时间倒序排列”，那联合索引就要把`user_id`放最左边，`created_at`放第二个，刚好匹配用户的查询习惯，索引才能生效。

#### 3. 唯一索引

保证这个字段的值不会重复，比如用户名、邮箱、订单号，建了唯一索引，就不会出现两个一样的订单号，从数据库层面保证了数据的唯一性，是核心业务字段的必备索引。

### 4.3 索引优化的5个核心技巧，避坑必看

#### 技巧1：只给区分度高的字段建索引

什么是区分度？就是字段里不同值的数量，除以总行数。区分度越接近1，索引效果越好；区分度越低，索引越没用。

- ❌ 错误：给性别字段建索引（只有男/女两个值，区分度0.5），查男性还是要扫一半的数据，根本没用；
    
- ✅ 正确：给用户名、订单号、用户ID建索引（几乎每个值都不一样，区分度接近1），索引效果极好。
    

#### 技巧2：绝对不要在索引列上用函数

比如你想查2024年1月1日的订单，写了`where DATE(created_at) = '2024-01-01'`，哪怕给`created_at`建了索引，也会直接失效。因为你给字段套了函数，数据库没法用索引排序，只能全表扫描。

- ✅ 正确写法：`where created_at >= '2024-01-01 00:00:00' and created_at < '2024-01-02 00:00:00'`，这样就能完整用到索引。
    

#### 技巧3：优先使用覆盖索引

什么是覆盖索引？就是你要查询的字段，全部都在索引里，不用再回到表里查数据，就像你要找的内容，目录里就有，不用再翻书。

- ✅ 覆盖索引：索引是`(user_id, created_at, status)`，查询`select user_id, created_at, status from orders where user_id = 123`，三个字段全在索引里，直接返回，速度超快；
    
- ❌ 非覆盖索引：查询`select * from orders where user_id = 123`，需要回表查其他字段，速度大幅下降。
    

给PM的核心建议：**设计需求的时候，不要动不动就要全量字段，要什么字段就查什么字段**，既能提升性能，又能减少数据泄露的风险。

#### 技巧4：索引长度不宜过长

不要给长文本字段（比如文章内容、长篇简介）建全量索引，TEXT类型的字段，几千个字符，索引会变得巨大，性能极差。

- ✅ 正确做法：只给前缀建索引，比如`CREATE INDEX idx_content ON articles(content(100))`，只索引前100个字符，够用的同时，大幅减小索引体积。
    

#### 技巧5：索引不是越多越好，定期清理无用索引

很多同学觉得，索引建的越多，查询越快，大错特错。

索引的副作用：每次插入、更新数据的时候，都要同步更新所有索引，索引越多，写入速度越慢，占用的存储空间也越大。

**给PM的硬性建议**：一个表的索引，不要超过5个；没用的索引，要及时清理掉。

## 第五讲 进阶实战：数据库性能优化的3个核心方案

这一讲的内容，属于进阶知识，产品经理不用会写代码，但必须懂原理、知道适用场景和坑，这样研发和你聊方案的时候，你不会一头雾水。

### 5.1 慢查询分析与优化

慢查询，就是执行时间超过阈值（比如2秒）的SQL查询，是拖垮系统性能的头号元凶。

#### 核心处理流程

1. 开启慢查询日志：把所有执行时间超过2秒的查询，全部记录下来；
    
2. 用`EXPLAIN`命令分析：这个命令会告诉你，这个查询有没有用到索引、是不是全表扫描、要扫描多少行数据；
    
3. 针对性优化：如果是全表扫描，就加合适的索引；如果是索引失效，就调整查询条件；如果是select *，就改成只查需要的字段。
    

#### 常见慢查询优化技巧，PM要记下来避坑

|慢查询问题|优化方案|
|---|---|
|全表扫描|给查询字段加合适的索引|
|用了select *|只查询业务需要的字段|
|嵌套子查询|改成JOIN关联查询|
|where里给索引字段用了函数|调整查询条件，避免索引失效|
|千万级数据不分页|做分页查询，限制每次查询的数据量|

### 5.2 分库分表的时机与方案

很多研发一上来就说要分库分表，显得技术很高大上，但其实分库分表的代价极高，**能不分就不分，实在扛不住再分**。

#### 什么时候需要分库分表？（满足任意一个）

|指标|阈值|建议动作|
|---|---|---|
|单表数据量|超过1000万条|考虑分表|
|单库磁盘空间|超过100GB|考虑分库|
|每秒查询量QPS|超过5000|考虑分库|

#### 两种主流分表策略

1. **按时间分表**：适合订单、日志等带时间属性的数据，比如按月分表`orders_202401`、`orders_202402`，是最常用、最容易实现的分表方案；
    
2. **按ID取模分表**：适合用户、商品等数据，比如按用户ID对10取模，分成10个用户表`users_0`到`users_9`，能把数据均匀分散到多个表里，扛住高并发。
    

#### 分库分表的核心代价（必须知道）

- 跨表、跨库查询极其复杂；
    
- 分布式事务难以保证，数据一致性风险高；
    
- 运维成本、开发成本指数级上升。
    

### 5.3 读写分离架构

#### 是什么？

大部分业务系统，都是**读多写少**，读写比例大概是9:1。比如电商系统，90%的操作是查商品、查订单、查推荐，只有10%是下单、改地址、支付这些写操作。

读写分离，就是用**一个主库专门处理写操作（增删改），多个从库专门处理读操作（查询）**，主库的数据会自动同步到从库，把读的压力分散到多个从库，不会因为大量查询把主库搞崩。

#### 必须注意的核心坑：主从延迟

刚写入主库的数据，同步到从库需要时间（几毫秒到几秒不等）。比如用户刚下单，立即去查订单列表，可能查不到，因为从库还没同步过来，用户会以为下单失败，重复下单，造成资损。

#### 解决方案

写操作之后的短时间内（比如1秒内），该用户的读操作强制走主库，保证数据一致性，避免主从延迟带来的问题。

## 第六讲 红线必守：数据库安全与备份

这一讲的内容，是产品经理必须推动落地的，因为一旦出问题，就是毁灭性的事故，轻则公司罚款、客户流失，重则负法律责任。

### 6.1 SQL注入防护：绝对不能碰的红线

#### 什么是SQL注入？

用户在输入框里输入恶意的SQL代码，拼接进系统的查询语句里，就能绕过登录、拿到整个数据库的数据，甚至删掉整个库。

举个最简单的例子：

系统的登录查询SQL是`SELECT * FROM users WHERE username = '用户输入的用户名'`，用户在用户名输入框里输入`admin' OR '1'='1`，拼接出来的SQL就变成了`SELECT * FROM users WHERE username = 'admin' OR '1'='1'`，这个条件永远成立，用户直接就能登录管理员账号，拿到所有用户数据。

#### 核心防护方案

**永远不要直接拼接用户输入的内容到SQL语句里，必须使用参数化查询**。现在主流的ORM框架（比如MyBatis、Django ORM）都会自动做参数化转义，从根源上避免SQL注入。

给PM的要求：提需求的时候，只要涉及用户输入的内容，必须提醒研发做SQL注入防护，尤其是搜索、登录、表单提交这些场景，这是绝对的红线。

### 6.2 数据备份：数据的最后一道防线

很多公司都是出了数据事故，才发现自己没备份，或者备份用不了，最后只能倒闭。数据备份，必须提前做好，不能抱有侥幸心理。

#### 必须遵守的3-2-1备份原则

- 3份数据副本：除了主库，至少还有2个备份副本；
    
- 2种存储介质：比如磁盘+对象存储（阿里云OSS、腾讯云COS），避免单一介质损坏；
    
- 1份异地备份：比如主机房在北京，备份在上海的机房，就算本地机房发生地震、火灾，数据还在。
    

#### 主流备份方案

- 全量备份：每天凌晨业务低峰期，备份整个数据库；
    
- 增量备份：通过binlog日志，记录每一次数据修改，就算出了事故，也能恢复到出事前1秒的数据。
    

### 6.3 数据恢复演练：备份不是摆设，能用才有用

很多公司有备份，但从来没恢复过，等真出事了，才发现备份是坏的，根本恢复不了，那就全完了。

给大家的硬性要求：**每月必须做一次数据恢复演练**，验证这3件事：

1. 备份文件能不能正常恢复；
    
2. 恢复需要多长时间（RTO），能不能满足业务要求；
    
3. 恢复后的数据是不是完整的，有没有丢失。
    

同时，必须把数据恢复的流程写成标准化文档，出了事故，直接按文档操作，不会手忙脚乱。

## 第七讲 落地指南：PM怎么把这些知识用到日常工作里？

学完了前面的内容，最后我们讲透，怎么把这些知识落地，变成你职场的核心竞争力。

### 7.1 PM必备的数据库技能分级清单，对照自查

|等级|核心能力|职场价值|
|---|---|---|
|认知级|懂3种主流数据库的区别，知道什么数据该存在哪|需求设计不跑偏，不会提“把订单数据存在Redis里”的外行需求|
|入门级|能看懂表结构，知道字段、主键、索引是什么，能看懂ER图|能看懂研发的技术方案，需求评审能跟上节奏，不会被研发忽悠|
|进阶级|设计功能时，能提前考虑数据模型，知道需求会不会涉及表结构变更，评估影响范围|需求设计提前规避90%的坑，需求评审通过率大幅提升，研发愿意和你配合|
|专业级|能和研发一起设计表结构，提出合理的索引建议，提前规避性能问题|成为研发认可的业务伙伴，能主导核心模块的设计，话语权大幅提升|
|专家级|能主导数据库设计评审，把控扩展性、性能、安全风险，制定数据备份和优化策略|具备产品架构师的能力，能负责中大型产品的整体设计，职业天花板大幅提升|

### 7.2 把数据库设计写进你的PRD，模板直接用

很多PM的PRD，只写页面和交互，从来不提数据模型，这是大错特错。一个专业的PRD，必须包含核心业务表的设计，研发一看就知道你懂行，不会瞎提需求。

给大家一个标准化的模板，直接套用到你的PRD里：

```Plain
## 订单表设计
### 1. 表名
orders

### 2. 表说明
存储用户订单核心信息，支撑订单创建、查询、状态流转全流程

### 3. 字段设计
| 字段名 | 类型 | 长度 | 允许空 | 默认值 | 说明 | 索引 |
|--------|------|------|--------|--------|------|------|
| id | BIGINT | - | NO | - | 订单ID（雪花ID） | 主键 |
| user_id | BIGINT | - | NO | - | 下单用户ID | 普通索引 |
| order_no | VARCHAR | 32 | NO | - | 订单唯一编号 | 唯一索引 |
| total_price | DECIMAL | 10,2 | NO | 0.00 | 订单总金额 | - |
| status | TINYINT | - | NO | 1 | 订单状态:1-待支付,2-已支付,3-已发货,4-已完成,5-已取消 | 普通索引 |
| username | VARCHAR | 50 | NO | - | 下单用户名（冗余） | - |
| ext_json | JSON | - | YES | - | 扩展字段，存储订单来源、渠道、活动ID等动态信息 | - |
| created_at | DATETIME | - | NO | CURRENT_TIMESTAMP | 订单创建时间 | 普通索引 |
| updated_at | DATETIME | - | NO | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 订单更新时间 | - |

### 4. 索引设计
- 主键索引：PRIMARY KEY (id)
- 唯一索引：UNIQUE KEY uk_order_no (order_no)
- 普通索引：idx_user_id (user_id)
- 普通索引：idx_created_at (created_at)
- 联合索引：idx_user_created (user_id, created_at)

### 5. 数据量预估
- 日新增订单：1万单
- 年数据量：365万单
- 3年数据量：1095万单，提前规划按月分表

### 6. 核心查询场景
1.  用户查询自己的订单列表：WHERE user_id = ? ORDER BY created_at DESC
2.  订单详情查询：WHERE order_no = ?
3.  后台订单统计：COUNT(*) WHERE created_at >= ? AND created_at < ? AND status = ?
```

### 7.3 给所有PM的4个终极忠告

1. **扩展性优先**：数据库设计一定要提前考虑业务变化，后期重构的成本是前期的100倍，不要等业务变了再救火；
    
2. **性能前置设计**：80%的性能问题，都可以在需求设计阶段规避，不要等上线了用户投诉了再优化；
    
3. **备份是底线**：没有备份，就等于裸奔，必须推动团队落实3-2-1备份原则和每月恢复演练；
    
4. **安全无小事**：SQL注入、数据泄露是红线，只要涉及用户输入，必须把安全放在第一位。
